# 올리 개발 AI 업무 규칙 — Engineering Skill Playbook
작성일: 2026-11-04 | 상태: 제안(검토용) | 코드 수정/배포 없음

> 이 문서는 Anthropic의 공개 Engineering 업무 스킬(code-review, debug, testing-strategy, deploy-checklist)의 절차를 참고해 **올리 전용**으로 재구성한 작업 지침이다. Anthropic 플러그인이 ChatGPT에 설치되거나 자동 실행되는 것은 아니다.
> 기존 `AGENTS.md` 및 `OLLI_COMMON_SOURCE.md`의 규칙을 대체하지 않는다. 충돌하면 **데이터 보존·기존 검증 계약**을 우선한다.

## 0. 최상위 우선순위
**사용자 데이터 보존 > 동기화 안정성 > 기존 기능 유지 > 새 기능 추가 > 코드 정리**

- 정상 동작 중인 CAS / revision / pending / blocked / conflict / session 복구 / Realtime을 '깔끔하게' 정리한다는 이유로 수정하지 않는다.
- Supabase / 브라우저 localStorage / 캐시 / 저장 데이터를 삭제·초기화하기 전에 미동기화와 서버 최신 상태를 반드시 확인한다.
- 중요한 저장 동작은 서버 저장 성공을 확인한 후에 로컬/UI를 반영한다.
- 사용자가 PC만 요청한 경우 모바일 UI는 유지한다. 반대 경우도 동일하다.
- UI 수정과 저장·동기화 로직 수정을 분리한다. 변경 범위를 좁게 유지한다.
- 원본 소스를 직접 수정한다. 중복된 wrapper/override/런타임 덮어쓰기 패치는 원칙적으로 금지한다.

## 1. 저장소와 원본 관리
- **실제 PC + 모바일 모노레포:** `vivizac/pc`.
- **PC 앱:** `apps/pc`, **모바일 앱:** `apps/mobile`.
- **공통 런타임 단일 원본:** `packages/common`; 각 앱의 runtime manifest가 공통 파일을 staging한다.
- **기존 `vivizac/mobile` 저장소**는 현행 공통 Production 소스라고 가정하지 않는다. 실제 배포 설정과 최신 `OLLI_COMMON_SOURCE.md`를 재검증한다.
- 필수 참고: 루트 `AGENTS.md`, `OLLI_COMMON_SOURCE.md`, `OLLI_REALTIME_STATUS.md`, 관련 앱의 모듈 문서.
- 역사적 감사 문서의 전환 중 기록보다 최신 운영 원본 설명과 실배포 구성을 우선하되, 차이가 있으면 먼저 보고한다.

## 2. 모든 개발 요청의 기본 처리 절차
1. **기준선 확보:** 작업 시작 시 `main` 커밋 SHA와 실제 Vercel Production 배포 SHA를 가능한 범위에서 기록한다.
2. **요구 범위 확정:** 바꿀 화면/동작/플랫폼/시나리오를 1~3문장으로 적는다. 기존 정상 동작과 보존할 데이터 명시.
3. **영향도 지도:** 실제 호출 경로, 읽기/쓰기 테이블·RPC·이벤트·캐시·PC/Phone adapter·정렬/출석/시간표 연동 여부를 조사한다. 추측은 '미확인'으로 표시한다.
4. **원본·원인 확인:** 현재 UI 렌더링 코드 및 기존 성공 코드, 관련 커밋, 재현 조건을 찾는다. 수정 파일을 최소화한다.
5. **작업 브랜치:** 여러 파일을 수정할 때 `main`이 아닌 브랜치에서 일괄 수정한다. 한 목적에 불필요한 리팩터링을 끼워 넣지 않는다.
6. **정적 검증:** 문법/타입, 호출 경로, DB 호환성, 권한·보안, 화면별 DOM/CSS 실제 selector와 이벤트, null/legacy 데이터.
7. **기능·회귀 테스트:** 아래 시나리오와 해당 기능 테스트를 실행한다. CI 상태가 '실행 중'이거나 실패이면 성공으로 보고하지 않는다.
8. **병합·배포:** 사용자 지시 또는 명확한 사전 승인이 있을 때만 최종 검증 후 `main`에 **한 번 병합 → 관련 Vercel Production 한 번 배포**한다. DB 구조 변경은 GitHub migration으로 남긴다.
9. **사후 확인:** 배포된 대상 프로젝트/URL/SHA/상태와 실제 기능을 확인한다. 실기기 확인이 없으면 '실제 렌더링 미검증'이라고 적는다.

## 3. 변경별 보호 게이트
### 관찰노트/저장/공통화 — 최우선 고위험
- PC → 폰, 폰 → PC 쓰기; 읽기만 했을 때 revision/수정 시각 불변.
- 동시 수정 시 CAS·conflict; 오프라인 → 재접속; pending/blocked; 세션 복구.
- iOS no-op 입력, dirty 상태, 모바일 전용 `olli-observation-autosave-phone-adapter.js` 보존.

### 시간표/출석/상담
- 기존 재원생 + 신규 학생 + 삭제 후 재등록 학생.
- 1회차/2회차 변경, 수업 이동, 보강, 대기, 체험, 취소, 출석, 사전결석, 과거/미래 주.
- 유치부 A/B, 초등 분리/통합, 실시간 수업 정원·학원 컨텍스트·권한.
- 상담 예약/변경/취소, PC와 모바일 날짜 피커, 로컬 우선 표시와 서버 신규 신호.

### UI 전용
- 요청된 기기/뷰포트만 변경; 기존 클릭/키보드/모달 닫힘 동작 보존.
- 실제 화면이나 스크린샷을 확인하지 못했다면 디자인 동일성·완료를 단정하지 않는다.

### DB 변경
- 읽기·쓰기 화면과 RPC의 영향도 선확인; 신규/이전 버전 데이터 하위호환.
- Migration 파일 생성 및 적용 이력 일치. 운영 DB 직접 SQL만 실행하고 끝내지 않는다.
- 데이터 파괴, 캐시 초기화, 강제 복구는 별도 명시적 동의 없이 수행하지 않는다.

## 4. AI 스킬 대응 관계
| 공개 스킬 | 올리 적용 |
|---|---|
| debug | 재현 조건 → 호출 흐름/상태 추적 → 원인 증거 → 최소 수정 |
| code-review | 보안·성능·정확성·회귀 위험과 사용자 데이터 영향 검토 |
| testing-strategy | 저장·동기화·시간표·상담·UI의 단위/통합/브라우저 회귀 설계 |
| deploy-checklist | SHA, CI, migration, Preview, Production, 롤백 판단 |
| write-spec (제품 기획 스킬) | 모호한 요청을 변경 범위·수용 기준·비목표로 정리 |

## 5. 작업 완료 보고 형식
- **변경 목적/범위**
- **변경 파일 및 실제 원본 경로**
- **데이터·동기화·PC/폰 영향도**
- **실행해 통과한 테스트(명칭·결과)**
- **실행하지 못한 검증(정확히 표시)**
- **브랜치 / commit SHA / main 병합 여부**
- **Production 배포 여부 / 대상 URL / 검증 근거**
- **잔여 위험 및 롤백 기준**

**금지 표현:** 확인하지 않은 변경을 '정상', 확인하지 않은 렌더링을 '동일', 실행하지 않은 테스트를 '통과', 배포하지 않은 코드를 '배포 완료'라고 말하지 않는다.

## 7. 적용 상태
이 문서는 업무 절차안이다. 올리 앱의 AI 실행 코드에 자동 연결되지 않았고, 앱 기능 변경·배포·DB 작업은 하지 않았다. 해당 문서를 개발 작업의 참조 기준으로 실제 적용할 때에는 기존 `AGENTS.md`와의 우선순위를 명시한다.
