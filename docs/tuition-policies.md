# 학원 교육비 설정

수입·지출 관리 상단의 **교육비 설정**에서 학원 기준을 관리한다. 학생정보 창에서는 해당 학생의 개별 약정을 별도로 저장한다. PC·모바일은 `packages/common/olli-tuition-common.js`와 CSS를 공유한다.

## 동작

- 주 1·2·3회 금액 카드가 기본이며 주 4·5회를 추가한다. 빈 금액은 미설정이며 0원과 구분한다.
- 신규 교육비표를 생성할 때 신규 등록 기준일과 기존 재원생 변경일(또는 계속 유지)을 선택한다. 적용 대상과 전후 금액을 미리 확인한 뒤 저장한다. 교육비표 금액은 덮어쓰거나 삭제하지 않는다.
- 개별 약정 → 해당 학생의 적용 교육비표 순으로 계산한다. 개인 금액은 적용 시작일·종료일·메모를 가지며 기본 교육비로 복귀하는 것도 새 이벤트로 남긴다. 종료된 개인 금액이 이전 개인 약정을 되살리지 않는다.
- 개별 금액은 해당 시점의 주간 횟수와 함께 저장한다. 횟수가 달라지면 `needs_review`를 반환하고 미확정 교육비를 예상 수입에서 제외한다. 시간표 저장은 완료한 후 교육비 수정 팝업으로 안내한다. 미래 수업 예약은 해당 적용일을 기준으로 수정할 수 있다.
- 재료비·교재비는 최초 등록 시 1회, 1~60개월마다, 또는 교육비 납부 주기마다 부과할 수 있다. 월 주기는 학생 최초 등록일 또는 공통 기준일을 선택한다. 이미 저장된 최초 등록일은 재등록으로 덮어쓰지 않는다.
- 교육비 변경은 해당 날짜 이후 시작하는 납부 주기에 적용한다. 월별 수입은 등록일 기준의 예상 납부일로 계산한다. 29~31일 월 납부는 짧은 달의 말일로 보정한다.
- 설정과 학생 금액은 원장 권한으로만 접근한다. 학생정보의 일반 저장과 교육비 저장은 독립적이다. 서버 성공 전에는 기존 값이나 입력 폼을 지우지 않는다.

## 데이터와 영향 범위

Migration: `supabase/migrations/20261019075624_academy_tuition_policies.sql`

추가되는 private 테이블은 학원별 설정/revision, 교육비표, 개별 약정 이력, 최초 등록일, 재시도 receipt이다. RLS를 켜고 anon/authenticated의 직접 접근을 차단한다. public RPC 3개는 기존 세션·원장 검증 함수를 사용하고 빈 search_path를 고정한다.

기존 `private.olli_academy_revenue_estimate` 원본을 정책 기반 계산으로 교체한다. 기존 finance overview 응답 필드는 유지하고 학생별 금액·미확정 목록을 추가한다. 출결/CAS/revision/realtime 저장 로직과 급여·지출 저장 함수는 변경하지 않는다. PC 시간표 서비스에는 성공 이후 읽기 전용 안내 이벤트만 추가한다. 모바일·명령 입력은 이미 존재하는 schedule-changed 이벤트를 사용한다.

기존 VIVIZAC(`VIVI-5578`)만 주 1회 110,000원 / 주 2회 150,000원 / 최초 워크북 70,000원 / 4주 기준으로 최초 초기화했으며, 후속 migration에서 매월 기준으로 전환한다. 다른 학원은 자신의 교육비표를 입력하기 전까지 미설정으로 표시한다. 원본 students/enrollments 데이터는 변경·초기화하지 않는다. 최초 등록일 보존용 부가 트리거만 추가된다.

## 적용 순서

운영 DB에 migration을 적용했으며, 실제 적용 이력 버전과 이 파일의 버전을 일치시켰다. PC와 모바일은 동일한 메인 커밋으로 함께 배포한다. 기존 브라우저도 공유된 public finance 응답 필드를 계속 읽을 수 있다.

교육비는 매월 기준이며 납부 주기 선택 항목은 두지 않는다. 실제 수납·미납·환불·일할 계산, 영수증 재발행은 이 예상 수입 기능에서 처리하지 않는다. 최초 등록일/정기 시간표를 기준으로 한 예상액이며 실제 결제 기록이 아니다.

## 검증

```sh
npm ci --prefix tests/tuition --ignore-scripts
npm test --prefix tests/tuition
node apps/pc/scripts/stage-common.cjs
node apps/mobile/scripts/stage-common.cjs
```

PostgreSQL(PGlite)에서 migration을 실행하고 신규·기존생 인상, 개인 금액 우선순위, 기간 종료, 횟수 변경, 반복 청구, 4주 설정의 매월 전환·월말 보정, 권한 차단, stale revision, 재시도 중복 방지를 검사한다. DOM 검사에서는 기본/추가 카드, 재료비 주기, 적용 전 미리보기, 저장 실패 입력 보존, 미래 예약 안내, 학원 전환 시 늦은 응답 폐기를 검사한다.

운영 DB 적용과 데이터 보존 검증을 완료했다. 브라우저/iPhone 시각 검증 및 운영 결제 대사는 별도 검증으로 남아 있다.


## 월 기준 및 삭제 학생 제외 수정

`20261019093240_tuition_monthly_deleted_filter.sql`은 기존 4주 설정을 매월로 변경하고 revision을 올린다. 교육비와 납부 주기별 재료비는 매월 등록일에 한 번 계산한다. 월말 보정, 별도 비용의 최초/개월 간격, 교육비표와 개별 약정 이력은 유지한다. 오래 열린 클라이언트의 `four_weeks` 입력도 매월로 처리한다.

현재 월·미래 월의 예상 수입 및 확인 필요 학생 목록은 집계 시작 단계에서 `status=active`인 현재 재원생만 포함한다. 휴원·퇴원·삭제 학생은 교육비 미설정 수와 개별 교육비 학생 수에도 포함하지 않는다. 삭제 여부는 `is_deleted`와 `deleted_at`을 함께 검사한다. 교육비 변경 미리보기도 현재 재원생만 포함한다.

과거 월은 등록일과 휴원·퇴원·삭제일로 확인되는 당시 재원 기간을 기준으로 계산한다. 현재 재원 상태를 과거 전체에 소급하지 않는다. 비활성 상태인데 날짜가 없는 레거시 학생은 과거 재원 기간을 추정해서 넣지 않는다. 단, 재등록·휴원 복귀를 여러 번 한 전체 이력은 현 students 타임스탬프만으로 복원할 수 없어, 이 계산은 실제 수납 장부가 아닌 보유 기간 정보에 기반한 예상액이다. 실제 수납·영수증 기록이나 학생·시간표 원본은 삭제하지 않는다.

이 후속 migration은 운영 DB에 적용했으며 Git 파일 버전을 실제 적용 이력과 일치시켰다.
