# 상담 예약 안내 알림톡

상담 대상 학부모에게 비비작 채널 명의의 안내를 보내고, 승인된 템플릿의 예약 버튼으로 기존 네이버 플레이스 예약을 엽니다. 예약 페이지와 네이버 예약 결과 수집은 만들지 않습니다.

## 코드와 영향 범위

- 공통 원본: `packages/common/olli-consultation-task-core.js`에 기존 상담 기준/월별 계산을 이동했습니다. 기존 `getConsultationDueTasksForStudent`는 같은 인자를 전달합니다. 서버도 이 원본을 사용합니다.
- 기존 상담 기준/진행상태 RPC, 관찰노트 CAS, realtime, pending, session 복구, 출석/시간표 저장은 변경하지 않습니다.
- 보호자 연락처는 별도 테이블에 저장하므로 이전 학생정보 저장 요청이 번호를 덮어쓰지 않습니다.
- 공통 UI: `olli-consultation-messages.js/css`. 설정 → 상담 예약 안내, PC·모바일 상담 목록에서도 접근합니다. 보호자 번호는 학생 등록·학생정보에서만 입력·수정하며, 상담 안내의 발송 대상 탭은 읽기 전용입니다. 원장/최고관리자만 접근합니다. 관리자/선생님은 발송 권한이 없습니다.
- 서버 원본: `packages/common/api/_lib/consultation-messages*.cjs`. 앱의 `api/consultation-messages.js`는 플랫폼 진입점입니다. 공통 파일은 기존 manifest/staging 절차로 포함합니다.
- 새 DB 객체만 migration에 추가합니다. 기존 학생·학원 설정 구조는 변경하지 않습니다.
- 기준 main: `f01811e1eccc4f0fbdc9ce6ee5674765f7c9b4ac`.

## 실제 사용 전 연결

1. 솔라피 계정에 기존 비비작 비즈니스 카카오채널을 등록합니다.
2. 재원생 정기 성장상담 안내 문구를 업체에 확인하고 카카오 템플릿 심사를 받습니다. 재원생 안내라도 자동 승인되는 것은 아닙니다.
3. 지원 변수는 `#{학원명}`, `#{학생명}`, `#{상담구분}`, `#{예약링크}`입니다. 본문은 승인된 템플릿과 같아야 합니다. ‘상담 예약하기’ 버튼은 웹 링크(WL), 모바일·PC 주소 모두 `#{예약링크}`로 등록합니다. 링크는 실제 네이버 플레이스/네이버 예약 URL을 사용합니다.
4. 새 migration을 적용합니다. 운영 DB에 별도 일회성 SQL을 남기지 말고 이 파일 그대로 적용합니다.
5. 두 앱의 운영 서버 환경에 기존 프로젝트의 `SUPABASE_SECRET_KEY` 또는 `SUPABASE_SERVICE_ROLE_KEY`를 설정합니다. 브라우저나 Git에 키를 넣지 않습니다.
6. 두 앱에 `OLLI_CONSULTATION_SOLAPI_CREDENTIALS`를 설정합니다. 값 형식은 아래와 같고, 실제 학원 UUID와 해당 학원의 솔라피 키를 사용합니다.

```json
{"<academy UUID>":{"apiKey":"<server-only API key>","apiSecret":"<server-only API secret>"}}
```

7. PC 운영 프로젝트에 최소 16자 이상의 무작위 `CRON_SECRET`을 등록합니다. PC에만 하루 한 번의 자동 작업이 있고 모바일에는 cron이 없습니다. 서버는 `VERCEL_ENV=production`에서만 발송합니다.
8. 모든 변경을 검증한 뒤 메인에 한 번 반영하고 각 앱 운영 프로젝트를 배포합니다. 자동 배포 비활성 설정은 유지합니다.
9. 먼저 원장 본인 번호를 테스트 학생의 확인된 연락처로 저장해 문구·네이버 링크·중복 방지·실제 발송 결과를 확인합니다. 이후 학생 등록·학생정보에서 실제 보호자 연락처를 등록하고 자동 발송을 켭니다. 실제 학부모 번호는 테스트에 사용하지 않습니다.

앱에 기본 표시되는 문구는 심사용 초안입니다. 실제 승인된 템플릿으로 바꿔야 합니다. API 키는 앱 설정에 입력하지 않습니다. SMS 대체 발송은 초기 범위에서 꺼져 있습니다.

## 자동 동작과 기록

- 자동 발송을 처음 켠 달부터 시작합니다. 기능 도입 전의 과거 상담을 일괄 발송하지 않습니다.
- 현재 재원·미삭제 학생, 확인된 보호자 번호, 안내 대상 체크, 활성 학원, 승인 확인 설정이 모두 필요합니다.
- 기존 상담 진행상태에서 완료된 상담은 제외합니다.
- 같은 학생의 같은 상담 예정 월에는 한 번만 발송합니다. 6개월·12개월이 겹치면 12개월 안내문을 한 번만 발송합니다. 새로운 상담 예정 월에는 새 안내를 보냅니다.
- 발송 전 DB 예약을 성공시킨 실행만 외부 API를 호출합니다. 동시 실행/네트워크 재시도로 중복 발송하지 않습니다.
- 예약 시 상담 기준·진행상태·학생 갱신시각·연락처/발송 설정 revision을 다시 확인합니다. 새 설정으로 바뀌면 다음 실행에서 다시 판단합니다.
- `reserved`: 발송 권한을 선점한 상태. 실행 중단으로 오래 남으면 업체 내역 확인이 필요합니다.
- `submitted`: 솔라피 접수 완료. 성공·읽음·예약을 의미하지 않습니다.
- `delivered`: 업체 조회에서 상태 코드 `4000`이 확인된 발송 성공. 읽음/네이버 예약 확인이 아닙니다.
- `failed`: 업체가 명확하게 거절/실패를 반환했습니다.
- `unknown`: 시간 초과/게이트웨이 오류/예상 밖 응답으로 업체 접수 여부를 확정할 수 없습니다.
- 자동 작업과 ‘발송 결과 새로고침’에서 접수된 메시지 결과를 조회합니다. 조회 버튼은 새 메시지를 보내지 않습니다.
- `failed`, `unknown`, 장시간 `reserved`는 자동 재발송하지 않습니다. 솔라피 발송 내역에서 실제 발송 여부와 실패 이유를 확인해 개별 처리해야 합니다. DB 기록을 지워 재전송하지 않습니다.
- 아직 외부 API를 호출하지 않은 대상은 실행 시간 한도에 이르면 다음 자동 실행으로 이월됩니다. 오류/연결 미설정은 cron HTTP 오류로 표시합니다.
- 번호 변경/발송 끄기는 이미 업체에 접수된 메시지를 취소하지 않습니다.
- UI 발송내역은 최근 300건을 표시합니다. 전화번호와 발송 본문은 앱 로그에 출력하지 않습니다.

## 검증

```bash
npm ci --prefix tests/consultation-messages --ignore-scripts
node --test tests/consultation-messages.test.cjs tests/consultation-messages-db.test.cjs
node --test tests/pc-build-closure.test.cjs tests/pc-self-contained-build.test.cjs tests/mobile-self-contained-build.test.cjs tests/vercel-monorepo-separation-contract.test.cjs
```

DB 테스트는 PGlite의 격리된 PostgreSQL에 migration을 적용하고 세션/학원 격리, 원장 권한, 재원생 필터, 중복 예약과 결과 보존을 확인합니다. 운영 DB를 수정하거나 실제 문자를 발송하지 않습니다. 기존 계산과의 비교 테스트는 위 기준 main commit이 필요하므로 CI checkout은 전체 이력을 가져옵니다.

브라우저 검증은 Playwright와 Chromium이 설치된 환경에서 `node --test tests/consultation-messages-ui.test.cjs tests/student-guardian-contact-ui.test.cjs`로 실행합니다. 테스트는 모의 데이터와 모의 API만 사용합니다. `OLLI_CHROMIUM_PATH`로 Chromium 실행 파일을 지정할 수 있습니다.

공통 파일을 실제 앱 폴더에 stage한 뒤 실행하는 이전 보안 테스트와, stage 이전의 단일 원본 테스트는 나눠 실행합니다. 기존 모바일 테스트 중 두 개는 이전 raw GitHub rewrite/오래된 cache-bust 버전을 기대해 기준 main에서도 실패하므로 이번 작업에서 수정하지 않습니다.

## 롤백

앱에서 자동 발송을 끄면 새 발송이 중단됩니다. 긴급 시 PC Vercel Cron도 비활성화합니다. 코드 롤백 시 새 연락처/발송이력 테이블은 보존합니다. 학부모에게 이미 전달된 메시지는 코드 롤백으로 취소되지 않습니다.

## 보호자 연락처 관리 위치

`olli-student-guardian-contact.js/css`가 PC·모바일 공통 연락처 편집 원본입니다. 학생정보의 저장 버튼으로 프로필 저장 후 같은 연락처 저장소의 보호자 번호를 저장합니다. 기존 상담 안내 설정에서 등록한 번호도 그대로 불러옵니다. 학생 프로필의 별도 phone 필드나 다른 로컬 캐시로 복사하지 않습니다. 연락처 조회에 실패하면 입력을 막아 기존 번호를 빈 값으로 덮어쓰지 않습니다. 권한은 기존 원장/최고관리자 범위를 유지합니다.

신규 등록 후 연락처 저장만 실패한 경우 입력을 유지하고 이미 생성된 학생 ID를 재사용하므로, 재시도 시 학생을 중복 생성하지 않습니다. 설정 화면에서는 연락처 등록/수정 기능을 제거하고 발송 대상과 번호를 조회합니다.

연락처 위치 변경 검증: 공통/서버/격리 DB·빌드 37건, 학생정보 시간표·픽업·피드백 담임 범위 8건, PC·모바일 브라우저 3건 통과. 기존 `pc-student-info-kinder-two-row` 테스트의 두 실패는 기준 main에서도 재현되는 오래된 바인딩/버전 문자열 기대이며, 관련 레이아웃과 날짜 입력 동작은 이번 작업에서 변경하지 않았습니다.

## 공통 안내문과 상담별 안내문

안내문 사용 방식은 `common`(전체 공통)과 `by_type`(학부·상담 단계별)입니다. 기존 설정은 공통 모드로 이어집니다. 초등부/유치부 × 1개월·6개월·12개월의 6가지 안내문을 각각 설정할 수 있고, 기존 3개월 상담 기준도 추가 항목으로 지원합니다. 각 항목에서 ‘공통 안내문 사용’을 켜면 기본 공통 안내문을 사용합니다.

공통 안내문은 항목을 따로 지정하지 않은 경우의 기본값이므로 승인된 공통 템플릿을 먼저 등록합니다. 개별 문구를 쓰는 항목에는 그 문구로 승인받은 알림톡 템플릿 ID와 승인 확인이 각각 필요합니다. 같은 문구만 쓸 경우 공통 템플릿 하나면 됩니다. 채널과 네이버 예약 링크는 학원 공통값을 사용합니다.

개별 안내문을 입력한 뒤 공통 모드로 전환해도 개별 내용은 보존됩니다. 개별 ID/문구를 수정하면 해당 항목의 승인 확인을 다시 받습니다. 채널 ID를 바꾸면 모든 승인 확인을 다시 받습니다. 이전 클라이언트가 새 설정 필드를 보내지 않아도 저장된 개별 안내문은 지우지 않습니다.

발송 시 가장 최근 상담 예정 월을 선택하며, 같은 달 6개월·12개월이 겹치면 12개월 템플릿을 선택합니다. 안내문을 바꿔도 발송 이력이나 같은 월의 중복 방지 기준은 초기화하지 않습니다.

초기 알림톡 migration 후 `20261020155449_consultation_message_templates.sql`을 순서대로 적용합니다. 새 migration은 알림톡 설정에 모드/개별 템플릿 컬럼을 추가하고 해당 설정 RPC만 확장합니다. 기존 보호자 연락처·상담 기준·관찰노트·시간표와 동기화 핵심 로직은 변경하지 않습니다.

## 학원별 사용 ON/OFF

설정 → 상담 예약 안내의 ‘상담 안내 문자 사용’ 스위치로 선택합니다. 기본값은 꺼짐이며 사용하지 않는 학원은 발송업체를 연결할 필요가 없습니다. 켤 때는 승인된 안내문과 발송업체 연결을 확인하고 현재 설정을 저장합니다. 끄면 별도의 저장 버튼 없이 즉시 사용 여부를 저장하고 자동 발송과 직접 보내기를 막습니다. 이미 업체에 접수된 메시지는 취소되지 않습니다.

끄기 전용 RPC는 사용 여부와 설정 revision만 변경합니다. 미완성 입력 때문에 끄기가 막히지 않으며 다른 기기에서 저장한 최신 문구·연락처·발송 이력을 보존합니다. 화면에서 수정 중이던 문구도 유지합니다.

마이그레이션은 `20261020150403_consultation_alimtalk.sql`, `20261020155449_consultation_message_templates.sql`, `20261020231237_consultation_message_usage_switch.sql` 순서로 적용합니다. 마지막 파일은 원장 권한의 설정 RPC에 끄기 동작만 추가합니다.


## 다학원 채널 운영 설계 (2026-10-21 결정)

결정: **본사 솔라피 계정/API 인증정보 한 벌**을 서버에서만 관리하며, 학원별로 **알림톡 사용 ON/OFF**와 **발송 채널(본사 공통/우리 학원)**을 별도 선택한다. 채널 선택만으로 발송이 시작되지 않으며, 기본 발송 상태는 OFF다.

### 보안·데이터 소유권

- 본사 API 인증정보는 단일 `OLLI_CONSULTATION_SOLAPI_CREDENTIALS` (추후 배포에서 본사 단일 스키마로 전환)로 보관한다. 기존 학원 UUID→API 키 매핑은 이 변경 전까지 **유지**한다. 비밀키를 SQL/클라이언트/Git에 기록하지 않는다.
- 본사 관리자만 **채널 레지스트리**에서 채널 ID와 채널별 승인 템플릿을 등록/검증/학원에 할당할 수 있다. 일반 원장 화면에서 임의 채널 ID 입력을 제거한다.
- 학원별 설정에는 `channel_mode = headquarters | academy`, 선택된 승인 채널 레지스트리 ID 및 revision만 저장한다. 본사 공통 채널과 개별 채널의 활성 여부, 허용 학원 및 승인 상태는 서버가 검증한다.
- 기본 선택은 `headquarters`이지만 **채널이 준비되지 않았거나 권한이 없으면 발송 불가**. 기존 `channel_id` 값은 새 구조로 이행할 때 삭제/덮어쓰지 않고 검증 후 매핑한다.
- 한 학원의 사용 OFF는 그 학원만 차단한다. 다른 학원의 예약, 전화번호, 발송이력, 템플릿, revision에 영향을 주지 않는다.
- API 서버에서 클라이언트가 보내는 channelId / templateId 를 믿지 않는다. `academy_id`의 서버 DB 설정에서 허용 채널과 승인된 템플릿을 조회한 후 발송한다. 승인된 템플릿은 발송하는 **실제 채널**과 연결되어 있어야 한다.
- `status`와 `send`는 기존 원장 권한 확인을 유지한다. 본사 채널 관리 기능은 별도의 **본사 관리자 권한**을 요구한다. 단순 `owner` 또는 `super_admin` 학원 권한을 본사 권한으로 간주하지 않는다.
- 전환 중 누락/비활성/미승인/채널-템플릿 불일치면 안전하게 발송 차단한다. 예약 DB 선점 전에 발송 가능 여부를 확인하고, 선점 시 설정·채널·템플릿 revision을 재검증한다. 이미 발송 접수된 건을 자동 재발송하지 않는다.
- 본사 공통 카카오채널 사용 허용 여부와 채널별 승인/브랜드·사업자 심사 조건은 솔라피 정책을 확인한 다음 실제 활성화한다. 비용·발송량은 학원별로 구분해서 집계한다.

### 올리 UI

- `상담 안내 알림톡 사용`: ON/OFF 스위치, **기본 OFF**, OFF 즉시 저장, 설정 문구 보존.
- `알림톡 발송 채널`: 라디오 `본사 공통 채널 사용` / `우리 학원 채널 사용`. 이 선택은 사용 ON/OFF와 독립.
- 본사 공통 채널 선택 시에는 본사에서 준비·허용한 채널과 템플릿 상태를 **읽기 전용**으로 표시한다.
- 우리 학원 채널 선택 시에는 등록/승인 요청과 상태(미연결/검토 중/승인/반려)를 보여준다. 연결을 승인하기 전까지 ON이나 실제 발송을 허용하지 않는다.
- 템플릿은 공통/학부·상담 시기별 6종(+3개월 선택) 구성을 유지하되, **선택된 채널에 승인된 템플릿**만 사용한다. 공통 채널을 선택했다고 개별 학원 문구가 자동으로 승인되는 것은 아니다.

### 구현 순서 및 회귀 검증 게이트

1. 본사 관리자 권한과 현재 DB의 학원/역할 모델, 기존 RPC, 솔라피 채널·템플릿 승인 데이터 구조를 조사한다.
2. 채널 레지스트리·학원별 할당 및 승인 상태·템플릿 매핑을 **새 migration**으로 추가한다. 기존 테이블/컬럼/발송 이력은 보존한다. 학원별 키→본사 단일 키 전환은 서버 변경과 migration을 함께 검증한 뒤 한다.
3. 공통 서버 발송 경로에서 DB 기반 채널 권한/템플릿 검증을 추가하고 상태·자동 발송·수동 발송을 통일한다. 예약과 동시성 보호를 유지한다.
4. PC·모바일 공통 UI 원본에 ON/OFF 및 발송 채널 선택을 추가한다. 본사 관리자 화면은 분리한다. 실제 학원 채널 ID 직접 입력을 허용하지 않는다.
5. 격리 DB·모의 솔라피 테스트: 학원 간 채널 오용, 미승인 템플릿, 본사 채널 허용/해제, ON/OFF, 채널 변경 시 이미 예약/접수된 건, 동시 발송, 과거 발송 이력, 이전 설정 호환성, 다른 기기 동기화, 모든 기존 상담 단계/재원생 필터를 확인한다.
6. PC·모바일 빌드, 관찰노트·시간표·학생정보 관련 회귀 테스트. 통과 전 main 병합/운영 DB 적용/배포 없음. 새 서버 키를 채팅이나 도구 출력에 노출하지 않는다.

**이 섹션은 확정한 설계와 구현 게이트를 기록한 것이며 실제 코드 전환이나 운영 적용 완료를 의미하지 않는다.**

## 학생 이름 조사 자동 치환 (2026-10-21)

- 학원에서 관리하는 학생 이름만 사용한다. **학교명·유치원명은 조회·추가·발송하지 않는다.**
- 솔라피에서 검수받은 본문의 변수 `#{학생이름_주제}`, `#{학생이름_주격}`, `#{학생이름_목적격}`, `#{학생이름_함께}`, `#{학생이름_방향}`은 각각 이름+은/는, 이/가, 을/를, 와/과, 으로/로로 변환한다.
- 받침이 ㄹ일 때 방향 조사는 '로'를 쓴다. 마지막 글자가 완성형 한글이 아닌 이름에 대해서는 조사를 추측하지 않고 발송을 거절한다.
- 템플릿의 원문을 변경하지 않고 변수값만 치환한다. 카카오 승인 템플릿과 변수가 일치해야 한다.
- 기존 `#{학생명}`은 호환을 위해 유지한다. 학교·유치원 이름 변수는 신규 지원하지 않는다.
- 추가 테스트: 실명 예시의 조사별 치환, 지원하지 않는 변수 차단, 학교·유치원 정보가 존재해도 알림톡 본문 및 변수에 포함되지 않는지 확인.
- 이 기능은 브랜치 코드·테스트에 반영되었으나 통합 테스트/운영 발송은 아직 실행하지 않았다.

## 다학원 채널 DB / 서버 1차 반영 기록

- 신규 마이그레이션: `supabase/migrations/20261021144500_consultation_channel_registry.sql`.
- 채널 레지스트리, 학원별 승인된 채널 할당, 채널별 승인 템플릿을 추가. 이전 설정과 발송 이력을 삭제하거나 덮어쓰지 않으며 기존 채널을 자동 승인하지 않는다.
- 서버 dispatch가 서비스 계정의 공통 솔라피 인증정보를 읽고, 학원·템플릿을 기준으로 `olli_consultation_channel_resolve` RPC를 조회하도록 변경. 승인되지 않으면 새 발송을 건너뛴다.
- 작업 중이며 **운영 적용 불가**: 실제 관리자센터에서 채널 등록·승인하는 인터페이스, 학원별 채널 모드 선택/저장 RPC·UI, 채널 승인 취소와 예약 사이 동시성 보호, 테스트·회귀 검증이 아직 필요하다.
- 기존 `OLLI_CONSULTATION_SOLAPI_CREDENTIALS` 문서 상의 학원별 매핑 예시는 신규 코드와 호환되지 않으며, 본사 단일 `{"apiKey":"...","apiSecret":"..."}` 형식으로 전환해야 한다. 값은 Vercel에만 직접 등록한다.
- 프로덕션 migration 적용, 병합, 배포, 실제 발송은 금지한다.

## 배포 전 연결 확인 (2026-10-21)

- 사용자가 Vercel `pc` 프로젝트의 Production 환경에 `OLLI_CONSULTATION_SOLAPI_CREDENTIALS`를 추가했다고 확인했다. 실제 키 값은 채팅/저장소에 수집하지 않는다.
- 환경변수 추가는 기존 배포로 소급 반영되지 않으므로, 테스트가 완료되기 전 재배포하지 않는다.
- 채널·템플릿 승인 상태를 발송 예약 직전과 예약 이후에 다시 조회한다. 승인 취소 시 발송하지 않으며 예약 내역은 중복 발송 방지를 위해 보존한다.
- 템플릿 확인 체크박스만으로 발송을 허용하지 않는다. ON 저장 단계에서도 본사 DB에 등록된 채널·템플릿 ID·승인 문구를 대조한다.
- 관리자센터 브랜치: `vivizac/vivicot-owner` / `work/consultation-channels-20261021`.
- **미검증**: 실제 DB migration 적용, 모든 상담 단계/개별 템플릿 회귀 테스트, Vercel 운영환경의 Secret 주입 확인, Solapi 실제 인증 요청, 예약과 승인 취소 간 강한 트랜잭션 일관성, 전체 PC·모바일 테스트. 이 작업들이 끝나기 전 main 병합 및 배포 금지.
